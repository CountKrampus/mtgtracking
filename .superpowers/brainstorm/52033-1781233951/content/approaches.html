3 Approaches to Flagging + Shadow Ban

Same decisions, different architectural trade-offs. Pick the one that fits best.

A

Unified ContentFlag model (Recommended)

One ContentFlag schema covers forum threads, forum posts, and chat messages via a targetType / targetId pair — the same pattern the app already uses in the Comment model. Shadow ban is a single isShadowBanned: Boolean field on User.

Pros

  • One flag queue, one review UI
  • Follows existing app patterns exactly
  • Shadow ban is a single fast field check
  • Least new code

Cons

  • targetType enum grows if more content types are added later
B

Separate flag models per content type

ForumFlag and ChatFlag are distinct schemas. Shadow ban is a separate ShadowBan model (mirrors the existing UserBan pattern).

Pros

  • Each model is type-safe with no nullable fields
  • Mirrors UserBan design

Cons

  • Two models, two routes, two admin tabs — duplicated logic
  • ShadowBan model adds complexity vs a simple boolean
C

Extend UserBan with a shadow type

Add shadow to the existing banType enum in UserBan. Flagging still uses a new ContentFlag model, but shadow ban reuses the ban infrastructure entirely.

Pros

  • Shadow ban appears in existing ban history / appeals flow
  • No new model needed for shadow ban

Cons

  • Shadow ban semantics differ from real bans — sharing a model creates confusion
  • Existing ban UI would show shadow bans to the user (breaking the silent isolation)
